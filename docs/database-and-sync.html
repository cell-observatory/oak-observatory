What OAK records

Database & sync

Each machine keeps a local database of its sessions, and oak sync shares what each database derives, and the agents’ files, with your other machines.

OAK keeps a local database on each machine: one SQLite file that holds what the observatory derives from that machine’s transcripts and store. If you run agents on more than one machine, oak sync shares what each database derives, and the files your agents read, among the machines you save with oak machine add. Each database then holds every machine’s records, so each machine can list, search and count the work of all of them. This page explains what each machine holds, what crosses between machines and what never does, and how usage is counted once across all of them.

The database across machines explains how local databases, record logs, SSH and a shared backup folder fit together. This page provides the command, settings and table reference.

The examples are the output of the commands on two synthetic machines: laptop, where the commands run, and build-box, a saved machine. Each has its own home folder under /tmp/obs-demo.

Multi-agent work across machines follows agents on several machines from start to review, and shows how each agent reads the other agents’ work from the local database.

The local database

The local database is a cache of the files OAK and the agents write: the transcripts, the Codex rollouts and the observatory’s store. A listing or a search reads it instead of walking those files. When its source files and complete record log are available, it can be rebuilt: the next catch-up reads the files again, and reads the archive, which the files no longer hold, back from this machine’s record log.

What it holds

The database holds:

  • each session, with the facts its listing shows: title, workspace, agent, model, tokens, edits and pending edits;
  • every prompt you typed and the prose that answered it, searchable with full-text search;
  • the metadata of each captured edit: its file, its line counts, its status and the hashes of its snapshots;
  • each tool call, with its target and its path within the project; workers and workflow runs; raised hands (a session waiting on a permission prompt, a question or your input) and waits; review comments;
  • the text of plans, memories and skills;
  • the usage of every assistant message, the readings each machine took of the account’s usage windows, and the spend Claude Code reported for each session (see Usage across machines);
  • the same rows from every other machine whose record log oak sync brings here, its raised hands included, each marked with the machine it came from.

It keeps no tool output and none of the content of the files your agents edit. The snapshots stay in the store, and the transcripts stay where the agent wrote them.

Where it lives

The database is one file per store, ~/.claude/claude-observatory-index/index-v1-<hash>.sqlite, beside the store’s configuration (under CLAUDE_CONFIG_DIR when that is set). The hash is the first 16 hexadecimal digits of a SHA-256 hash of the store folder’s path. The file never sits inside the store, which can move to a network share where SQLite is unsafe. OAK creates the folder with mode 0700 and the files with mode 0600. oak query --status names the file:

$ oak query --status --table
database: /tmp/obs-demo/laptop/.claude/claude-observatory-index/index-v1-8a32a33b1a640ebb.sqlite
3 session(s), 0 archived · 432.0 KB · caught up 07:35:32

The database file itself is never copied to another machine: oak sync never reads it. Each machine builds its own from its files and from the record logs it pulls.

How it stays current

Each command that lists, searches or queries first catches the database up with the files on disk. One pass of directory listings and file stats finds what changed since the last catch-up, by each file’s device, inode, size and modification time. The catch-up reads only what changed, from a byte cursor kept for each transcript. One process catches up at a time. A reader gives the catch-up two seconds, checked between sessions, and leaves one that would read more than 64 MB to the background.

The catch-up can stop short: another process may be catching up, or more may be left than a reader takes on. Then oak sessions, oak search, oak inbox and oak notify --watch read the files, as they did before the database existed. oak query answers from the database as it stands, and says how current it is. When files were left to read, the command also starts oak __index-build in the background, at most once a minute; that build is how a machine with many transcripts gets its first database. The capture hooks never open the database, so an agent’s tool calls never wait for it. Once oak sync has run on a machine, each hook there starts that build in the background instead, at most once a minute and at once when it raised, changed or lowered a hand, so what an agent does reaches the machine’s record log while it works, whether or not anything reads the database there.

When it is caught up, the database gives those four commands the same answers as the files. oak inbox and the listing’s syncedHands also list the other machines’ raised hands, which only the database holds, read from it as it stands, caught up or not. The terminal app reads it through these commands and through the long-running oak process it keeps for its views. VS Code also reads it in its own process where the editor’s Node.js has node:sqlite, and a JetBrains IDE keeps one oak query --serve running for the checks it repeats.

The database needs Node.js 22 (22.16 or newer) or 24 or newer, whose built-in SQLite has full-text search; no Node.js 23 release has it. The CLI refuses unsupported Node.js before running any command; only the capture hooks still record edits there. An editor that embeds core can still read files when its own Node.js lacks SQLite. On a supported runtime, OAK_INDEX=off also selects file readers; database queries then have no database to answer from.

What it costs on disk

The database grows with the text of the prompts and answers, not with tool output. It takes about twice that text, plus about half a kilobyte for each tool call, a kilobyte for each edit, and a third of a kilobyte for each assistant message’s usage. On a synthetic machine on Linux, with Node.js 24.18 and SQLite 3.53.1, the database took 123 MB and the record log 84 MB. That machine held 1,200 Claude Code sessions and 60 Codex rollouts, 398 MB of transcripts with 38 MB of prompts and answers, 40,165 tool calls, 2,397 edits and 69,750 assistant messages.

Nothing caps the database, because archived sessions are kept. Deleting its folder reclaims the space; the next listing builds it again from the files that remain and from the record logs, this machine’s own included. oak doctor and oak query --status show its size.

How to turn it off

With OAK_INDEX=off in a command’s environment, OAK neither builds nor reads the database, and every listing reads the files. With OAK_INDEX=shadow, OAK reads the files and records each answer in which the database would have differed, in shadow.jsonl beside the database.

How to query it

oak query answers from the database in JSON, for agents and scripts. Each answer carries its columns and rows, whether a limit cut them, and how current the database was (freshness, whose sources name each machine with its origin: local for this machine and replica for every other one, a different thing from a session’s origin of replica, which marks a row made from a copy of another machine’s edit log); --table prints each row for reading and --arrays returns rows as arrays. The named queries are:

QueryWhat it lists
sessionsEvery machine’s sessions the database holds, newest first.
edits · filesCaptured edits with their line counts, and the files they touched, with how many sessions and machines edited each. A file in a git repository is its repository and its path from the repository’s root, so one repository’s file, cloned at different paths on different machines, is one file; a file outside any repository is its absolute path.
prompts · searchA session’s prompts in order; prompts and their answers ranked by full-text search (BM25), a prompt weighted three times its answer.
delegatedAgents started from this machine’s briefs, including its remote starts, with OAK-derived states and their workers.
workersSubagents and workflow agents, with their session’s phase.
notesPlans, memories and skills.
syncEach machine whose rows the database holds, and how current they are.
usage · readingsTokens in a window by machine, model, session, day, agent or account; the readings each machine took of the account’s windows.
schemaThe tables, their columns, and each named query with its parameters.

Sync across machines

oak sync shares the agents’ state among this machine and its saved machines, the machines oak machine add saved in herdr (oak machine list shows them). A run is pull-only: this machine reads each saved machine over SSH, with that machine’s own oak, and writes only its own disk. The one thing it asks of another machine is that it bring its own record log up to date first (below). With a backup folder set, it also writes its own files there (below). No machine writes another’s files. A saved machine whose user name differs from this machine’s refuses before it reads anything, so sync needs the same user name on every machine. Every machine you sync with is trusted with the skills, agents, commands, memories and plans your agents follow, since a change to them on one machine reaches the others.

What each machine keeps

Sync carries files by family, and each family has a placement: where its files are kept.

FamilyKept
Claude Code’s auto memory (each project’s memory/ folder), plans, skills (but skills/synced/, which Claude Code manages), agents and commandsOn every machine, merged three ways against the last version the machines shared.
OAK’s record logs (oak-records), and each session’s edit log, comments and agent record (oak-log, oak-meta)On every machine.
Claude Code transcripts with their subagents/ and tool-results/ folders, Codex rollouts, and OAK’s snapshots and hook eventsOn the machine that made them and on the backup.

Each machine publishes what its local database derives of its own sessions to a record log, an append-only log in its store (records/<machine>/), which oak sync keeps on every machine. A machine publishes as its database catches up: before it answers another machine’s sync run, which asks it to catch up first, for up to five seconds (what is left, such as a first build too large for that, goes on in the background, and a later run brings it); as its agents work, once oak sync has run there, through the background catch-up each capture hook starts at most once a minute, and at once when it raised, changed or lowered a hand; when OAK lists, searches or queries there (as the terminal app and editors do); at the status line’s oak usage call, on each render that asks for the database’s totals (about every ten minutes once those totals are whole); and before OAK’s cleanups. A raised hand is published at once, but a permission prompt only once it has stood its wait (five seconds, or 90 under Codex’s Auto-review), as the machine announces it. A listing or a background usage read that another machine runs there catches it up too (see Multi-agent work across machines). Every machine’s database therefore lists every machine’s sessions and searches their prompts and answers, without their transcripts.

Every machine also keeps each other machine’s inventory, the list of its files that a run reads, which oak sync status shows under index:. oak sync fetch <session> brings one session’s files here, from the machine that made it or, when that machine cannot be reached, the backup. Later runs keep a fetched copy current, and evict copies, least recently fetched or refreshed first, once they pass 2048 MB (sync.cacheMB).

A project lands in this machine’s own folder for it. Sync matches a project by its repository’s origin, its path under the home folder, or the network share it is on. A repository cloned at ~/src/app on one machine and ~/code/app on another is therefore one project. oak sync family <family> everywhere|backup|on-demand|off changes where this machine keeps a family (the text families take only everywhere or off). oak sync exclude <machine|project> stops this machine pulling from a saved machine, or pulling a project’s files; the other machines still take this machine’s files unless they exclude it too. The full rules, including how a transcript is extended, are in REMOTE.md.

Both editors list those sessions too, each with its machine’s name, in Switch Session and in VS Code’s Timeline session selector. Picking one shows what its records say of it and offers to fetch it here. VS Code and JetBrains also list each machine saved in herdr as the terminal app does, by asking it with oak sessions --machine, and review a session picked there on its machine (see A session on another machine). The terminal app lists a saved machine’s sessions from its records when oak sync read that machine in the last ten minutes and nothing there may be running. A machine may be running something when one of its sessions was active in the last two hours, as its records or the files the last run saw there say, or a hand it raised in the last day is still up; the terminal app then asks the machine over SSH. A session’s raised hand travels in its records, and the other machines read its phase from that hand. What only that machine can see right now, such as whether a session with no hand up is working, or a running worker, is never current in its records.

Review still runs where the files are. Undo and Redo change files on disk, and every decision writes the session’s edit log, which only the machine that runs the session writes. The terminal app’s Review tab therefore runs each decision on the machine that runs the session, over SSH with that machine’s own oak. No decision acts on the copies that sync keeps elsewhere.

How sync conflicts close

Two machines can change the same lines of a memory, plan, skill, agent or command file, or hold two versions of one with none in common, as when one file was made on each machine before they first synced. Sync then keeps both: this machine’s file stays where it is, and the other machine’s version is kept in sync’s conflicts/ folder as a sync conflict. A transcript whose copies differ, as when one session was resumed on two machines, is also a sync conflict. Sync never puts its other copy beside this machine’s in Claude Code’s folder. oak sync now reports each sync conflict, oak sync status lists the open ones with their ids, and oak inbox lists them with the raised hands:

$ oak sync now
oak sync: pulled 1 file, 453B
  build-box   1 file, 453B; 1 conflict
  conflict: plans import-speedup.md from build-box: kept as conflicts/build-box/plans/import-speedup.md

$ oak inbox
sync conflict  plans import-speedup.md from build-box — its copy is /tmp/obs-demo/laptop/.claude/claude-observatory/sync/conflicts/build-box/plans/import-speedup.md; edit your file or delete the copy (`oak sync resolve 93c600a3db06` deletes it)

$ oak sync resolve 93c600a3db06
resolved plans import-speedup.md: the copy from build-box is in sync's trash (/tmp/obs-demo/laptop/.claude/claude-observatory/sync/trash/2026-10-31/plans/import-speedup.md), and this machine's file stands

A sync conflict closes in one of two ways. Edit your file to hold what you want of both versions: your edit is the merge, the next run closes the conflict, and the other machines take your file. Or delete the other machine’s copy with oak sync resolve <id>: your file stands, and the other machines take it at their next run. A diverged transcript closes only by deleting its copy. Every surface offers the same two ways out where it lists the raised hands:

  • The terminal app lists the open sync conflicts after the raised hands in its i list. Enter on one offers both ways out: both copies opened in your editor, or the other machine’s copy deleted, after you confirm.
  • VS Code groups them above the sessions in the Timeline’s session list. Each row has two links: one opens both copies side by side in a diff, and the other deletes the copy after asking.
  • JetBrains lists them above the workspaces on the Overview’s Sessions tab, with the same two choices.

Which deletes travel

Sync passes on only the deletes you make on purpose. Two kinds become a tombstone: a session deleted with oak sessions --delete, and a memory, plan, skill, agent or command file removed on one machine. The next run carries each tombstone to the other machines, which apply it there. A file edited after its delete keeps the edit and comes back, and oak sessions --undelete brings a session back everywhere. Claude Code’s own retention sweep is no delete, and it never propagates. A run never pulls a transcript older than this machine’s cleanupPeriodDays, which Claude Code here would sweep again; oak doctor warns when that setting is unset, once a run has set sync up here. A family that goes missing whole, or loses more than half of its files (and more than three) at once, as one on an unmounted drive does, passes no delete on.

What never leaves a machine

These stay on the machine that holds them:

  • the local database file: each machine builds its own, and only its rows travel, in the record log;
  • Claude Code’s .claude.json (a hash of its account id travels in the record log), its settings (sync reads cleanupPeriodDays from settings.json and nothing else), its credentials, its per-process sessions/ files and shell-snapshots/;
  • Codex’s auth.json, config.toml and databases, and the home folder’s .ssh, .gnupg, .aws, .netrc and .git-credentials;
  • OAK’s preferences, and the backup key, which moves only when you copy it (below);
  • the live process and terminal themselves. Records can carry the last observed delegated state, pane identity and worker metadata; current evidence must still be read on the owning machine, over SSH when needed.

Transcripts, rollouts, snapshots and hook events leave the machine that made them only for the backup, for a machine that fetches them, and for a machine that keeps that family everywhere. The record log does go to every machine you sync with. It carries your prompts and the answers to them, and each tool call’s target, such as a shell command of up to 300 characters, a file path, a URL or a search query. It also carries the text of plans, memories and skills, review comments, raised hands with what each waits on, edit metadata, workers and usage. oak sync family oak-records off on a machine stops it pulling the other machines’ logs; what it already holds stays, in records/ and in its database. SECURITY.md lists what each log holds.

The backup

The backup keeps a copy of every machine’s sessions outside the machine that made them, so a machine that is wiped can be restored. It is either a saved machine or a folder every machine reaches. A saved machine pulls every machine’s sessions (oak sync backup <label>, set the same on every machine, that machine included). A folder (oak sync backup --folder <path>) can be a network share, a network-attached storage (NAS) device or an external disk. Into a backup folder each machine writes its own files, encrypted on the machine before they are written, under a key the folder never holds.

How to choose the backup

oak sync setup asks on a terminal where the sessions are backed up (nowhere else, a saved machine, or a folder), makes or brings the folder’s key, and previews a first run. Off a terminal it takes --none, --machine <label> or --folder <path>, and, for a folder that already holds a backup, --key-from <machine> or --import-key. The folder’s path is each machine’s own, where that machine mounts it:

$ oak sync setup --folder /tmp/obs-demo/share/oak-backup

set up: the backup is the encrypted folder /tmp/obs-demo/share/oak-backup (key 0487-644a-0f3e-0668)
a new backup key was made here. Keep a copy where you keep passwords (`oak sync key --show`): without it the backup cannot be read. On each of your other machines, run `oak sync setup --folder <the folder's path there> --key-from <the label that machine saved this one under> --replace` (`oak machine list` there shows the label; a key that machine kept for another folder is kept beside this one), or `oak sync setup` there.
…

Setup then prints the first plan, as oak sync plan does. Change the backup later with oak sync setup again or with oak sync backup, which takes a saved machine’s label, --folder <path> or --none. The terminal app, VS Code and JetBrains make the same choices through the CLI, which keeps them in OAK’s prefs.json, and a copy of them in oak sync’s sync/settings.json, which brings them back where an OAK older than 0.11.0 rewrote prefs.json without them (see Upgrading from 0.10.0). In the terminal app, the options window’s SYNC section hands the terminal to oak sync setup; VS Code has OAK: Sync; JetBrains has its status bar menu and the OAK Settings page. The terminal app’s SYNC section and the JetBrains Settings page offer setup once a machine is saved; the status bar items in VS Code and JetBrains appear once sync is in use.

How to keep the key

The key is 32 random bytes, made when a new backup folder is set up and kept in this machine’s store at sync/key with mode 0600. oak sync key prints its fingerprint, a short name that tells two keys apart and reveals nothing of either. Each other machine that writes to the folder needs a copy:

  • oak sync key --from <machine> copies it from a saved machine over SSH, which answers only your own user name.
  • oak sync key --show prints it, with a warning, for a password manager. oak sync key --import takes it back from standard input; on a terminal, it asks for the key and shows nothing of what you paste. It never takes the key as an argument, which your shell’s history and ps would keep.
build-box$ oak sync key --from laptop
kept the backup key 0487-644a-0f3e-0668 at /tmp/obs-demo/build-box/.claude/claude-observatory/sync/key

A different key already kept here is replaced only with --replace, and the old one is kept beside it. Without the key the folder cannot be read, by OAK or by anyone. If every copy of the key is lost, the backup is lost with it. To start a new one:

  1. Set up a new backup in an empty folder with oak sync setup --folder <path>, which makes a new key.
  2. On each other machine, run oak sync setup --folder <path> --key-from <machine>. oak sync key --from alone refuses a key that does not open the folder still set there.
  3. Remove the old folder by hand.

What the backup folder holds

Everything in the folder is sealed with AES-256-GCM, using Node.js’s own cryptography, under keys derived from yours. Its names are keyed hashes, a few fixed words, and the numbered parts of each machine’s record in the folder. No file name, path, session id, project, host name or user name appears in a name or in the clear. The folder holds:

  • oak-backup, a marker holding a known text sealed under the key, which shows at once that a key is wrong;
  • machines/<keyed name>/, each machine’s record in the folder, which that machine alone writes, as numbered parts (seg-000000000001, then a whole snapshot every 32 parts);
  • objects/ and packs/, the content, by keyed names: objects of 1 MB or more one to a file, and smaller ones sealed one by one into packs of up to about 32 MB.

Someone who can read the folder but has no key learns only what the names, sizes and times show: how many machines write there, how much each writes, and when. OAK reports, and never uses, anything that does not open or that opens to other content than its name says, so it detects altered or substituted files. The folder cannot protect itself from someone who can write it: removing or replacing whole files makes runs fail and restores incomplete. Nothing is ever removed from objects/ or packs/. A session deleted with oak sessions --delete stays there, so that an undelete can bring it back, and so do the parts of a record log that a compaction replaced.

How to restore a reinstalled machine

The folder knows each machine by its host name and home folder. A machine reinstalled with the same name and home, holding its key again, takes over its record in the folder explicitly with oak sync setup --restore, or by answering yes when setup asks on a terminal. Until then, the machine neither restores from the folder nor writes to it. Each machine also keeps a random writer id (sync/writer), sealed into every part it writes, and a note of the parts it wrote. Two machines that share a host name and home, such as two virtual machines made from one image, therefore never take each other’s sessions. Here build-box, reinstalled, takes its record back:

build-box$ oak sync key --import < key.txt
kept the backup key 0487-644a-0f3e-0668 at /tmp/obs-demo/build-box/.claude/claude-observatory/sync/key

build-box$ oak sync setup --folder /tmp/obs-demo/share/oak-backup --restore

set up: the backup is the encrypted folder /tmp/obs-demo/share/oak-backup (key 0487-644a-0f3e-0668)
this machine took over the folder's record under its name (last written 2026-10-31T11:35:39.377Z by build-box (home /tmp/obs-demo/build-box)): the next run restores its sessions from it
…

The next runs restore the machine’s own files from the other machines and the folder, at most 2 GB from each source in a run. They restore everything but the sessions it cleaned up or deleted on purpose, and a transcript older than its cleanupPeriodDays waits in the folder until its retention keeps it. The machine’s record log comes back too, and with it its archive. That holds even when the machine was used before its first restore: a compaction of the log it began anew replaces only that log, so the other machines keep the one it kept before and read it with the new one, and the folder keeps it to restore. A partly restored segment stays outside a base’s coverage until its final length is known; reaching the end of the received copy is not enough. Old history from a different writer lifetime is read before the selected base, so a clock set back during reinstall does not let an old segment overwrite that base’s newer text. If two disconnected bases disagree, an existing database keeps its selected base; a rebuilt database uses filename order to choose, and the uncovered logs stay available. A machine reinstalled under another host name or home is a new machine in the folder, and brings the old one’s sessions over with oak sync fetch <session>.

When a session’s store folder is lost

A session’s store folder can be lost without a cleanup: removed by hand, lost in a crash, or lost when a reinstalled machine is used before its first restore. The next capture then makes the folder again, with a new log. Sync keeps what the copies held of the earlier folder as a session of its own, <session>_earlier-<generation>. That session comes back to its machine, which lists it as the session’s earlier history:

$ oak sessions

Unknown workspace · 1 session

~/code/app · 1 session

Neither a session cleaned up with oak clean and captured into again, nor one deleted with oak sessions --delete, gets an earlier history.

The archive

The local database keeps what a session did after its files are gone. The archive is those rows: the prompts and answers, the edit metadata, the tool calls, the workers, the comments and the usage of sessions whose files no longer hold them. It is not the terminal app’s archived list (B), which only hides resolved, inactive sessions whose files are still there.

What outlives a session’s files

  • Resolved or cleared records. Resolving a session, or oak clean --resolved, drops its decided edit records from its store’s log; the database keeps them, marked cleared.
  • A cleaned store. oak clean (or an editor’s Drop) removes a session’s store; the database records the session first, and keeps its edit records, marked cleared. Every surface that cleans up does this, except where an editor’s Node.js has no node:sqlite: there, what the session did since the database last caught up goes with its files.
  • A swept or deleted transcript. Once a session’s transcript, rollout and store are all gone, the session itself is archived, with when and why: cleaned when OAK’s cleanup removed its store, retention when it was older than Claude Code keeps transcripts, and missing otherwise.

Named queries leave archived sessions out, and --archived or --all brings them back, marked. Here the laptop’s 45-day-old transcript is gone, as Claude Code’s 30-day retention removes it:

$ oak query search --text websocket --table

The archive’s source of truth is this machine’s record log, which oak sync keeps on the other machines and in the backup. When the database starts again from a new file, as on a machine set up again or after its folder was deleted, it reads the archive back from that log.

If a part of this machine’s log goes missing while the database is reading it back, compaction waits: the unread part may hold sessions that only another machine or the backup can restore. Until then, deleted sessions can still have text in the log that sync carries. oak doctor names the log and its missing or incomplete parts. Run oak sync now with every saved machine and the backup available, then oak sessions. Sync brings back the missing parts. If a complete run finds that none holds a copy, the next listing stops waiting and compacts what remains. A failed run, an excluded or disabled machine, a run limited to selected machines, or a backup that cannot be read proves no loss.

How to forget a session

Only a deliberate delete forgets. oak sessions --delete <id> purges every row of the session from the database at once, its full-text entries included, and SQLite overwrites what the delete freed. The delete then reaches every machine: oak sync carries it as a tombstone, and each machine’s database forgets the session as it applies the record log. Compaction retains the purge itself, so a machine receiving only the record log still forgets the session, including after a database rebuild. The next compaction removes the session’s text from the complete segments it replaces; an incomplete restored segment waits for its remaining bytes. On a machine set up again, a session from before that is deleted there leaves the copies of the log the machine kept before once oak sync brings that log back to it. A backup folder keeps what it holds of the session, sealed (above). Deleting a session in the terminal app, VS Code or JetBrains forgets it the same way; where VS Code’s Node.js has no node:sqlite, the database forgets it at its next catch-up. The delete leaves the session’s transcript where the agent wrote it. Only the session’s usage stays, without the session, because the account was billed for it; oak sessions --undelete gives it back with the session:

build-box$ oak sessions --delete s-build-import
removed session s-build-import from Observatory and purged its captured edits (its transcript is untouched; `oak sessions --undelete s-build-import` puts it back in the pickers, and the next `oak sync now` brings back what of its edits the backup folder holds)

On a machine that does not use oak sync, deleting the database folder and this machine’s record log (records/ in the store) forgets everything that only they held. With oak sync, the other machines and the backup keep copies of this machine’s record log, and the next run brings it back. To forget a session on every machine, use oak sessions --delete. oak uninstall --all --purge-store forgets the sessions whose stores it removes in this machine’s database and record log, and a transcript the purge leaves is added to the database again from the file. Another machine forgets what those stores held once a run brings it this machine’s record log. While this machine’s OAK still answers its runs, it also lets its copies of the stores go, as after any cleanup; a machine that does not reach this one again keeps its copies, and can keep what its database holds of them. oak demo --clean forgets the demo’s sessions and their usage, which no record log carries.

Usage across machines

Your Claude account’s 5-hour and weekly shares are the account’s, not one machine’s, so each machine’s token and dollar estimates must count the work of every machine signed in to that account. The local database counts each message once across every machine whose usage it holds.

How each message is counted once

The database keeps one row for each assistant message, by its message id, at its largest snapshot: Claude Code writes one message as several lines while it streams, and the line with the most tokens counts. The row carries the message’s input, output and cache-creation tokens, its cache reads apart, its model, its list-price cost, and the session, machine and account it belongs to. A window’s total is one query over those rows, so a message counts once however many machines hold a copy of its transcript, and work on separate machines adds up. Tokens are input plus output plus cache creation, as Claude Code counts them. In this example, fetching the build box’s session onto the laptop changes no total:

$ oak usage --window week --by machine

A window counts this machine’s rows and the rows of other machines billed to the account this machine is signed in to. Each machine names that account by a hash of the account id in Claude Code’s .claude.json. A machine with no Claude Code login of its own counts the one account its saved machines name. When they name two or more, it counts every machine’s rows and shows no other machine’s reading. oak usage --window 5h|week|bill|month|day|all --by machine|model|session|day|agent|account breaks a window down, and oak query usage returns the same breakdown as JSON.

Rows of other machines arrive in their record logs. For a saved machine whose record log oak sync does not keep current here, a background read at most every five minutes (oak __usage-records over SSH) brings its usage rows and readings, never a conversation. "machineUsage": false in OAK’s prefs.json turns that read off. This stops new usage pulls and cached brief additions; account totals still count the message records already in the database, including records delivered by oak sync.

How a session counts the agents it started

A session that starts agents, such as subagents or a workflow’s agents, uses their tokens as well as its own. Claude Code writes each agent’s turns to a transcript of its own in the session’s folder, and the database counts those turns as the session’s. The usage readouts show two labelled figures for such a session: own, its own turns, and with N agents, its own turns and those of every agent it started. A session that started no agent shows one figure. The session lists (oak sessions, the terminal app’s session rows and the editors’ session lists) show a session’s own tokens. In oak usage --window --by session, a session’s line counts its agents, and the line under it, own, counts its own turns:

$ oak usage --window week --by session

The other surfaces are the status line, the terminal app’s status row, the Session tokens section in VS Code’s Stats panel, and JetBrains’ Stats panel. oak usage --breakdown --by session shows a session’s own line first and its line with its agents under it, and names the session that started each agent. oak usage --json carries the session with its agents as sessionTreeTokens, and oak query usage --by session carries agents, own_tokens, own_cache_read and own_cost beside each row’s totals. A row from a machine whose OAK predates this release does not record whether an agent made it, so a session with such rows has no own figure, and its line shows the total alone. A Codex subagent’s thread counts as a session of its own.

Usage pulls do not require oak sync setup. They are triggered by oak usage, the terminal app’s minute usage refresh and the editors’ minute polls, with a five-minute throttle shared across pollers. No open reader means no periodic usage pull. Each refresh can fetch up to 20 pages per peer; a backlog continues on the next refresh. Unreachable machines retain their last data. Hover the usage readout to see each peer’s record stamp, with stale, failed or partial pulls marked. Stats and JSON carry the same stamp; it is separate from when a quota percentage was measured.

Bill-day settings travel in the same incremental usage records: oak usage --gpt-bill-day 14 on one machine reaches saved peers on their next successful pull from it, normally within five minutes plus a poll and the SSH round trip while a reader is active. No sync setup is needed. An offline peer or a backlog takes longer.

How readings are kept

A reading is a share of one of the account’s windows (5-hour, weekly or per-model weekly) as one machine measured it, with its reset and when it was measured. Where this machine has no current reading of a window, the readouts show the freshest reading another machine of the account took inside that window, and name that machine. Readings and spend reports are kept whole for 35 days, and then as the account’s usage over time: one reading of each machine, agent, kind and hour, and one spend report of each session and day. Message rows are kept forever, with a daily rollup that answers windows longer than 35 days. oak query readings lists the readings, newest first.

How an older OAK still counts

When a saved machine’s OAK predates oak __usage-records and refuses it, this machine asks it for its readings instead (oak __usage-brief, which an earlier 0.11.0 pre-release answers). Its readings are shown as before. The successful readings-only answer establishes that capability; only then do the totals and estimates add what it measured of its own turns, once per machine. An unsuccessful refresh keeps that last capability. As soon as the machine supplies message-level records, even an empty page or a page outside the current windows, its aggregate is no longer added. Copies of another machine’s transcripts may be attributed to the machine that first indexed them; missing rows under a host’s name never establish a readings-only capability. oak doctor describes the fallback. A machine on 0.10.0 or older answers neither, and supplies no reading and no usage until it is updated.

How the status line uses the totals

The bundled status line takes its figures from the oak usage call it makes on each render. Once the database’s totals for the account are whole, it calibrates its token and dollar estimates against them (usageTotals in oak usage --json), and then reads no transcript of its own. Those totals count each message once across every machine whose usage the database holds. They are whole when a catch-up of everything has finished in the last 15 minutes, no session failed to enter the database, and their windows match the ones the status line measures. Without them (an OAK without the database, a database still building, or a window that turned over between two reads), it scans this machine’s transcripts instead and adds the account’s usage on the other machines in the same windows. With "machineUsage": false it scans this machine’s transcripts and adds nothing. A window it takes from a saved machine’s reading is named in a dim label ahead of the windows, such as (build-box).

When an account has no five-hour limit

Some accounts have no five-hour limit: Claude’s Ultra plan, once the account is verified, answers its usage read with no 5-hour window. OAK records when the account last answered with no 5-hour window and when it last answered with one, on each machine, and carries both answers to the other machines as readings. While the newest answer on any machine of the account is a no-limit one, no surface shows a 5-hour readout, whatever 5-hour share a session or a machine holds. The surfaces are the status line, the terminal app, both editors and oak usage --json, and their weekly readouts are unchanged. The first answer that carries a 5-hour window brings it back in Stats, oak usage and the Claude Code status line. Terminal and editor status bars omit this window regardless of the account. Database versions and usage display

The current database schema is 8. Schema 7 records account billing days. Schema 8 adds findings and their retirement records, and the parent session used to exclude an agent’s descendants from edit-time notes. See How agents share what they know. Schema 5 added delegated, the agents started from briefs; their rows travel in the record log. oak query delegated lists this machine’s tracked agents, including its remote starts, followed by their workers. --all includes closed agents and workers=false omits workers. SQL can read every machine’s delegated records in the database.

Schema 6 records the one-hour subset of cache writes, the worker, provider, speed and geography, the price-table version (priced) and whether the cost is an estimate (cost_approx). Five-minute and one-hour cache writes have separate rates. Older messages are repriced when the price table changes. A session’s own usage and its usage with its agents are labelled separately. Derivation version INGEST_VERSION 6 uses the current worktree’s root for file paths and records native child sessions’ parents. OAK also defers a Codex rollout that changes while it reads it, so a growing file cannot publish half-derived session facts.

The terminal and editor status bars omit the five-hour window. Stats, oak usage and the Claude Code status line keep it when the account has that limit. In every status bar the month’s dollar figure follows the mo reset: ~ marks a list-price estimate; an actual charge has no tilde. The Claude Code status line compacts long model and gauge rows before wrapping them. The headline in oak __usage-brief reports measured tokens; a quota projection is not a measured count.

Sync refuses a small file that shrinks while being sent, retries an incomplete restored record segment from its saved offset, and repairs key permissions when importing the same key. A family symlink cannot expose the current or replaced backup keys even after a store move, and transcript paths are checked before reading headers so credential symlinks are never opened. Restoring preferences and saving a setting share a lock, preventing a concurrent save from being overwritten.
