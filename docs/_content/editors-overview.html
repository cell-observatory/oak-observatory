The Overview is the editor-side equivalent of the terminal app's Observatory and Review tabs — a master-detail board over your worktree fleet, in a panel. Its left nav has five tabs; selecting a row fills the right side with that thing's change map.

The tabs

  • Sessions — sessions from every machine in one list, newest by last activity first. Sessions belong to the machine where that workspace runs. Selecting a local session switches what the whole panel reviews.
  • Workers — every agent in herdr on this machine and each saved machine, every agent OAK started, and recent Claude Code and Codex sessions across the repository's worktrees. The reviewed machine comes first. Rows lead with the tab or session title and show machine, kind, OAK state, tokens and last activity.
  • Processes — the background shells the session launched.
  • Tasks — the session's numbered task list, each with its strict span.
  • Workflows — every multi-agent run, unfolding to its phases and agents.

In both VS Code and JetBrains, Sessions merges every machine’s rows in the chosen order. Newest by last activity is the default; Oldest, Name A→Z and Name Z→A also order across machines. Raised hands and sync conflicts stay ahead of ordinary sessions wherever they are shown. Search matches titles, ids, workspaces, models and machine names across the whole list. Active only retains live sessions, sessions whose workers are still at it, pending edits and the review pin. Under a session whose workers are still at it, one row counts them by state; a click opens it into a group per state, those waiting on a person first, each worker with its title, model, lines, edits, pending count, tokens and last activity, and a click on a worker opens its own live log. Active only is on by default and already hides inactive, fully reviewed sessions. With it off, sessions with a recorded completion collect into one ▸ N done row per machine, closed at first. Click to open it and see those sessions grouped by workspace; click again to close. The panel remembers open folds while it lives. A done session folds even with edits left to review, and the fold row counts them (▸ N done · M pending). The reviewed session and active workers stay visible. A new turn leaves the fold; search reveals matching done sessions that pass Active only. Age alone does not put a session in the done fold. Sessions in which nothing happened are not listed (Sessions and agents gives the rule).

The CLI lists sessions on the workspace host. Remote-SSH, devcontainer and Gateway windows therefore list that remote host’s sessions. Copied transcripts from another machine and bridge pointers without local conversation records are excluded. VS Code and JetBrains also list the sessions of each machine saved in herdr (oak machine list), as the terminal app does. Switch Session, the Timeline’s session selector and the Sessions tab merge each saved machine’s sessions with this machine’s, keeping a machine badge on each remote row. The session selectors, Sessions and Workers share each machine’s listing. Each machine is read in the background with oak sessions --machine: all of them at once, each at most every ten seconds and within 45 seconds. This machine’s list never waits for them. One short line per machine stays above all session rows, including during search: when it was read or synced from records, whether it is reading again, whether it has not answered yet, or why it could not be read and when it last answered. Picking one of its sessions reviews that session on its machine (see A session on another machine). The session lists in both editors also merge each other machine’s sessions whose records oak sync brought to the local database, with that machine’s name and when oak sync last read it (or when its records arrived, for one it does not read). Picking one shows what its records say of it, read-only, and offers to fetch it here (oak sync fetch). After the fetch its conversation opens here, but this machine does not list its captured edits, and it is reviewed on the machine that made it. Database & sync explains what each machine keeps.

In Workers, Active only keeps working, waiting and blocked agents and hides finished subagents. With Active only off, finished subagents fold into one “N done” row that opens with a click. A session whose process has ended without a clean finish reads “gone”. Workers uses oak fleet --json; saved-machine reads share the session cache and deadline and never hold up the panels.

Shell process output

Processes sits directly after Workers in both the tabs and grouped columns, for every reviewed session here or on a saved machine. It lists the session’s shells and its workers’ shells, running first, including recorded Codex exec sessions. The panel stays visible while reading or unavailable, and an empty answer says No shells in this session. Turn off Active only to include finished shells.

Select a running or finished shell in Processes to follow its output in Timeline’s Feed tab. VS Code and JetBrains both run oak processes --follow <id> --session <session> --json in the background. Selecting another subject stops the previous follower.

For a session on a saved machine, the follower adds --machine <label> and reads the file there. Remote reads share the 45-second deadline and wait at least ten seconds between requests. Failed reads appear in the Feed panel.

The feed shows a plain-text tail of up to 16 KiB, with terminal controls removed. Claude Code workers’ shells appear alongside the parent’s shells. Codex exec sessions show the output recorded by exec and write_stdin; Codex records no separate output file to watch.

The change map

Selecting a row fills the right with its change map — the Folders strip, one tile per changed directory ranked by lines and colored by review status, and the churn-ranked Files ledger. A summary bar totals the scope, and selecting a row opens its feed in the Timeline's Feed tab, showing what it's doing (a session row also connects the tab, to read that session's conversation). Clicking a Folder tile steps the review nav to that folder's first pending edit; clicking a file opens its diff.

The panel's toolbar carries inline controls, in place rather than as a pop-up: a search field (session text is a substring; file paths also accept regular expressions), a filter dropdown for the file-type buckets and extensions, and a sort dropdown (four orders — newest, oldest, name A→Z, name Z→A). The filter button names what it is narrowing by and the sort button names the order in force, so the toolbar reads back its own state. Each file shows the exact time of its last change beside it.

💡
Group all five tabs

The nav can show every tab side by side in one group — Sessions, Workers, Processes, Tasks, and Workflows as columns you can drag and fold — since what is happening is one question, not five.

Click a worker in Sessions or Workers to open its own live log in the Timeline’s Feed panel, including workers nested under an agent started from a brief. Each worker follows its parent session and workspace on its owning machine. VS Code and JetBrains keep the selected worker’s log after it finishes, with its exact recorded end time, and update it if it resumes. Worker rows under a saved machine read there over SSH, at least ten seconds between reads. A failed read is shown in the panel. In-process workers do not open herdr tabs.

Conversation search also searches enabled saved machines in parallel and labels every hit with its machine. Task Accept, Reject, Clear and Clear Completed run on the session’s selected machine. See remote tasks, search, navigation and replies for deadlines, keyboard controls and replies in Timeline/Feed.

Open workspace window

In Observatory’s Sessions list or a session picker, choose Open workspace window (the window button in VS Code/Cursor; right-click the row in JetBrains). The session’s folder opens in its own editor window. Saved machines use Remote-SSH in VS Code/Cursor or Gateway in JetBrains, with SSH instructions if Gateway cannot open. A missing folder or a session with no workspace is refused. One action opens one workspace.

The window pins the session and opens its pending changes in the stacked editor, ten per page. With nothing pending, OAK says so and opens no empty tab. It reveals Review, File History and the Observatory Timeline, and focuses the Overview with Sessions, Workers, Processes, Tasks and Workflows side by side and the change map beside them. Your saved view placements stay in place. A terminal named OAK runs oak; an existing OAK terminal is reused. JetBrains needs its Terminal plugin for that terminal. An already-open workspace receives the same request without restarting the editor; a request is used once and expires after ten minutes.

Use one window per machine and workspace instead of combining mounted folders in a multi-root workspace. OAK, git and file watching then run on the machine that owns the files, and a stalled extension host affects only that window.
