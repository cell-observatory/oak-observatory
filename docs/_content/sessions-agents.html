Everything OAK records hangs off a session — one conversation with a coding agent. A native session can spawn more agents, sit beside siblings in other git worktrees, or run as one arm of a workflow. OAK correlates all of them, so a fan-out reads as a single account of who did what.

Session

A session is one conversation with a coding agent. The agent assigns it an identifier and writes its transcript to disk; the observatory keeps one store per session and presents the session by name — the name you gave it (Claude Code’s /rename, or a rename on claude.ai or the Claude app), else the title claude.ai shows for it under Remote Control, else the agent’s own title, else its first prompt — with the raw identifier available in tooltips.

If Claude Code resumes a session after its workspace moves, it can keep the same session ID in two project folders. OAK uses the most recently written local transcript and its latest recorded working directory, even when that file starts with the old history. Session lists, --session, the inbox and search follow that copy. Sync extends the newest local copy and fetches the newest copy a machine holds; backups retain both files. Workspace labels keep the recorded paths rather than combining different sessions through symlinks or junctions.

With Remote Control on, Claude Code keeps a session’s name on claude.ai and never writes it back to the transcript, so OAK reads those titles from your account (at most every five minutes, with Claude Code’s stored login) and caches them. Listings read only the cache; a failed read keeps the local names and oak doctor reports it. oak titles shows the last read, oak titles --refresh reads now, and oak titles --off turns the read off.

One session at a time is under review. The Sessions tab in both editors merges sessions from every machine in one list, newest by last activity first. Search, Active and the four Sort choices cover the whole list; raised hands and sync conflicts lead wherever shown. Selecting a local row changes which session every window shows. In VS Code and JetBrains, each remote row carries its machine badge, with one short state line per machine above the rows, and selecting a saved machine’s session reviews that session on its machine (see A session on another machine). Rows carry the title, edit count, tokens, duration, model, store size and last activity, including zero counts; a click on the store size opens that session’s store folder, as does the store button beside Export in the review toolbar. The folder opens in the system file manager, or, when VS Code or Cursor is connected to another machine (Remote-SSH, WSL, a dev container), in a new editor window on that machine. Sessions known from sync records join the same order; selecting one offers to fetch it. A session whose workers are still at it, working or waiting on a person, has a row under it counting them by state; a click lists them, those waiting on a person first.

Delete, on a Sessions row, in VS Code’s session pickers and in the terminal app’s session picker, removes a session from OAK. Its captured edits are purged, while the transcript itself is not deleted. The confirmation says so, in the words oak sessions --delete uses (with a backup folder set, the edits are purged here only), and names any edit still pending review, because the purge drops the snapshot its undo would need. oak sessions --undelete <id> lists the session again, without its edits, unless the backup folder of oak sync holds a copy of them: after an undelete, the next oak sync now brings that copy back (see The backup folder). The local database forgets a deleted session’s prompts and answers on every machine, and keeps its usage (see Database & sync).

A session in which nothing happened is not listed: no captured edit, no tokens and no reply from the model, such as Claude Code closed at its prompt, a /model or /login and nothing more, or a prompt answered only by an API error. A session that may still be running stays listed before its first reply: the current session, the one under review, a Claude Code session whose process is still running, a session waiting on you, a Codex turn in progress, or any session active in the last five minutes. Titles are one line of plain text, without markdown heading markers or line breaks, whatever their source. A session whose workspace is recorded nowhere is grouped under Unknown workspace.

Codex titles come from its thread-name index or rollout, with the first real user prompt as the fallback. Injected instructions and environment context are skipped. A title that only hands the task to a markdown brief, such as Execute TASK.md, gives way to the heading on the brief’s first line. The brief is read on the machine where the session ran, first 8 KB only, at the path the prompt names (relative to the session’s workspace, absolute, or under ~); if it is gone, the title stays as it was. A heading or prompt longer than 64 characters is titled by its first phrase, up to its first sentence end or clause break (an em dash, colon, semicolon or comma), when that phrase has at least two words and 12 characters; a first sentence that ends within 64 characters is kept whole rather than cut at a clause break inside it, and a name that Codex or you gave stays whole. A prompt that is itself a brief is titled by its heading, a Codex Auto-review thread is titled after the session it reviews, and a thread of Codex’s own memory-writing agent is titled Codex memory update. Codex records no token usage for that agent, so its rows show edits without tokens. Codex runs each Auto-review approval (approvals_reviewer = "auto_review") as a thread with a rollout of its own, so the session lists and conversation search on every surface leave those threads out (on a saved machine, once it runs this version), and a review thread is never the session a workspace resolves to. Naming one with --session still opens it, oak sessions --all lists them, and usage figures still count their tokens. The session lists, the terminal’s session line and the Stats headers show the same title. Mirrored transcripts and bridge pointers without local conversation records do not appear in the listing or become the current session.

Needs you

The capture hooks record what each session is waiting on — a permission prompt and the tool it guards, an unanswered question, an input wait — the moment the agent raises its hand, and lower it the moment the agent moves on: the call a permission prompt was for returns, the agent starts another call, or the next prompt lands. A subagent shares its parent's session, so a permission prompt keeps the agent that asked for each of its calls: a call's start lowers only the calls its own agent asked for, a prompt that names no call is lowered by any call's start, and a subagent's prompts come down when the subagent finishes. Claude Code reports only its edits and commands to OAK's hooks, so there a prompt on another tool — a web fetch, an MCP call — stays up until the next edit or command, the end of the turn or the next prompt.

A raised hand reaches you three ways: a desktop notification; a needs you list — oak inbox, the i overlay on the terminal app's Observatory and Review tabs, the group atop the editors' session selector and attention markers in the Sessions tab — ordered permission first, then question, then input, oldest first, each row saying what it waits on and for how long; and a one-key jump to the most urgent one (h on the terminal's Observatory and Review tabs, VS Code's status-bar ⚠ chip, and ⌥⌘X then h in both editors, Ctrl+Alt+X then h on Windows and Linux). The observatory only says who is waiting; the answer stays in the agent's own terminal. With oak sync, the needs you list also holds the other machines' hands, each labelled with its machine, as their records brought them; the one-key jump goes to this machine's own (see Multi-agent work across machines).

Desktop notifications:

  • A hand is announced once per machine, by whichever surface sees it first. The options turn them off or on, per kind of wait.
  • Another machine's hand is announced when oak sync brings it, at once and naming that machine: a permission prompt travels only once it has stood its wait there. Clicking it focuses nothing here, since it is answered on that machine.
  • A permission prompt is announced only if it is still unanswered five seconds after it went up, so a prompt you answer at once posts nothing. The message each surface shows in its own window for it (a note at the bottom of the terminal app, a notification in VS Code, a balloon in JetBrains) waits the same way, here and under Auto-review below. The hand itself rises at once on every surface.
  • In a Codex session whose approvals go to Auto-review (approvals_reviewer = "auto_review", read from the session's rollout), Codex's reviewer answers the prompt rather than you, so it is announced only if it is still up after 90 seconds, the time Codex gives its reviewer. Codex hands a prompt to you only when the review cannot finish, and such a prompt is announced up to 90 seconds late. A prompt whose approved command Codex left running in the background, such as a server still running when its yield_time_ms passed, stays up until Codex reports the command’s end, the agent starts another call, or the turn ends, so it can still be announced after the 90 seconds.
  • On macOS, when OAK runs in iTerm2, Ghostty, WezTerm or kitty, the terminal posts the notification under its own name, and clicking it brings the terminal forward. An editor or a herdr pane, which does not pass the terminal's notifications on, posts through terminal-notifier when it is installed (brew install terminal-notifier): a newer notification for the same session replaces the older one, and clicking it brings forward the app OAK was started from and, from the terminal app or JetBrains, selects the session in an open OAK terminal app. Without terminal-notifier it comes from osascript, which macOS shows as Script Editor and opens on a click, and oak doctor says so.
  • On Windows it is a toast that Windows heads with Windows PowerShell, the app that posts it.

Live state and review history

herdr reports whether a pane is working, idle or blocked. When Codex asks a question and keeps working, herdr reports its pane as blocked; Observatory shows that pane as working, with ? question beside it (see Observatory). OAK records whether its captured edits are resolved. Observatory keeps active panes and unresolved sessions visible; resolved inactive sessions are archived, with B to include them again.

The agents inside a session

A session is rarely alone. It can spawn subagents, each with its own transcript and role; it can run as one arm of a workflow; and it sits beside siblings in other worktrees of the same repository. The fleet unifies every running agent across those worktrees into one board. Multi-agent work across machines covers the sessions on your other machines.

Agents started with oak agent start --brief have OAK-derived states: starting, working, waiting, blocked, errored, done and gone. Workers under those agents have their own logs and no native tab. The three-machine workflow shows start, list, wait, review and close.
