Start agents from briefs on your laptop and saved machines, follow their workers, wait for their reports, and review the changes where they were made. OAK tracks the work; each agent runs in its native Claude Code or Codex CLI, with its chatbox, in a herdr tab. After review, merge the branch with git and close the agent’s tab.

This walkthrough uses three synthetic machines: laptop, build-box and gpu-box, each with a separate working tree. The commands and output below came from the built CLI with synthetic session files, processes and reports. Stand-ins for SSH and herdr routed requests to each machine’s isolated home; no model was called. Only the home paths have been normalized to /tmp/obs-demo/<machine>. The example demonstrates OAK’s behavior, not the agents’ ability to solve these tasks.

The database across machines explains how each machine builds its database, exchanges record logs and uses an encrypted backup on shared storage. Database & sync provides the command and settings reference.

Set up your agent to delegate

oak agent setup installs opt-in guidance for Claude Code and Codex. It lists every destination and managed entry before asking for permission to write. It also checks whether herdr is installed and running; oak doctor --fix repairs a missing setup.

$ oak agent setup --check --json
# A JSON plan lists each destination, its managed part, and its state.
$ oak agent setup
# Choose defaults, review the listed writes, then confirm.
$ oak agent setup --yes --project
# Install in the current repository without a prompt.

User setup installs skills/oak-delegate/SKILL.md and agents/oak-builder.md under CLAUDE_CONFIG_DIR, or ~/.claude. It places a marked block in CODEX_HOME/AGENTS.md, or ~/.codex/AGENTS.md, and adds Bash(oak agent:*) to Claude Code's settings. The documented permission syntax limits the rule to the oak agent command prefix.

Setup offers each CLI's configured model and effort, then preserves your choices in OAK's prefs.json under agents. It offers existing ~/.gradle, ~/.npm and ~/.cache directories as Codex writable roots. --yes accepts these defaults. Codex always receives the agent's output folder; repeat --writable-root <dir> to add roots for one launch.

Project setup uses the repository's .claude directory and AGENTS.md. Its preferences live in .claude/claude-observatory/prefs.json and override user defaults when starting agents there. Each scope has an oak-agent-setup.json ownership manifest. OAK compares installed content with that manifest before changing it. Edited content is reported and kept, including during removal.

--check reports missing, current, outdated and edited content; --json emits the plan for scripts. --remove removes only OAK's managed content, after confirmation or with --yes. oak update refreshes installed user guidance and the current repository's guidance. oak uninstall removes both; oak uninstall --project removes only the current repository's setup. Run these commands in each repository with project setup. Repeating setup without changes writes nothing.

The parent uses its own agent kind unless the brief or a flag specifies another kind. It writes a brief beginning with # Title, followed by the goal, scope, constraints, proof and deliverables. It starts the agent, runs oak agent wait <id> in the harness's background facility, reads report.md, reviews in OAK, merges, closes the tab and checks oak agent list --all for cost.

The delegated agent leaves changes uncommitted. It writes report.md with “What changed”, “Tests (before and after results)” and “Not verified” sections, plus a binary diff that includes untracked files. It stays in its assigned worktree and output folder, uses synthetic data, raises a hand when blocked and starts no nested agents. oak-builder excludes Claude Code's Agent tool.

Before starting work, and before editing a file other agents may touch, agents check oak query files, oak query search --text …, oak query delegated --all and oak query findings. When another active agent has pending edits to a file you are about to edit, OAK adds a note to your context; coordinate before editing. The guidance names oak agent tell <id> <text> for parent messages, oak agent start … --after <id…> for dependencies, and oak finding add "<text>" [--path <file>] for shared facts.

Create and track worktrees

oak agent start --kind codex --brief <file> --worktree [<base>] creates a Git worktree beside the repository, named by the agent id, on branch oak/<id>. The base defaults to HEAD. The repository must exist and be clean; keep the brief outside it. An agent started with --cwd in an existing linked worktree also records its path, branch and base.

The owning machine saves changed-file counts, added and removed lines, commits ahead and behind the base branch, merge state and the reading time. These fields travel with delegated records to other machines. Agent lists and the Workers rows in the terminal app, VS Code and JetBrains show a summary such as 3 files · +120 −8 · not merged.

OAK reads at most one stale worktree per refresh, with at least 30 seconds between readings of that worktree. Each read has a 1.5-second deadline, 256 KiB of output per Git command and 1 MiB of untracked file content. It reads the Git index and changed paths, without scanning session history. Binary files count as files but have no line totals. A failed or bounded-out reading is shown as unavailable. Ahead and behind use the moving base branch when available; change totals use the recorded base commit.

oak agent close --remove-worktree <id> removes a worktree only when it is clean and its changes are merged. A clean branch is merged when its tip is contained in the base branch, or their trees agree. After applying an uncommitted diff in the parent, reconcile the agent worktree before removal. oak doctor names worktrees without an agent row and merged worktrees whose agent is gone or closed. It suggests the close command and never removes them itself.

Prepare the machines and briefs

Install OAK, its capture hooks and herdr on each machine, with Node.js 22.16 or a later 22, or 24 or newer. The CLI enforces that runtime requirement. Save remote machines with oak machine add <label> <ssh-target>; --machine uses that saved label. For bidirectional sync, save each machine on the others. Sync requires the same user name on both ends.

$ oak machine list --json
[{"id":"machine-build-box","label":"build-box","target":"builder@build-box","session":"default","enabled":true,"selected":false},{"id":"machine-gpu-box","label":"gpu-box","target":"builder@gpu-box","session":"default","enabled":true,"selected":false}]

Place each brief on the machine that will run it, beside its working tree. OAK does not copy a remote brief or clone the repository. The first Markdown heading becomes the task title. The three briefs in this example are docs-brief.md on laptop, login-brief.md on build-box, and dates-brief.md on gpu-box. The login brief contains:

# Retry the login test

Make the change, run its checks, and report the result.

Start the agents

The brief’s filename, without -brief.md, supplies the id unless you pass --name. --cwd names the working tree. The output folder defaults to <id>-out beside that tree; --out overrides it. The completion report defaults to report.md there; --report overrides it. Start the documentation task locally and the other two on saved machines:

$ oak agent start --kind claude --brief /tmp/obs-demo/laptop/work/docs-brief.md --cwd /tmp/obs-demo/laptop/work/app
Started docs (claude) in herdr tab "docs: Document the retry policy", pane p1. Its report: /tmp/obs-demo/laptop/work/docs-out/report.md
$ oak agent start --kind claude --brief /tmp/obs-demo/build-box/work/login-brief.md --cwd /tmp/obs-demo/build-box/work/app --machine build-box
Started login (claude) on build-box in herdr tab "login: Retry the login test", pane p2. Its report there: /tmp/obs-demo/build-box/work/login-out/report.md
$ oak agent start --kind codex --brief /tmp/obs-demo/gpu-box/work/dates-brief.md --cwd /tmp/obs-demo/gpu-box/work/app --machine gpu-box
Started dates (codex) on gpu-box in herdr tab "dates: Cache parsed date formats", pane p3. Its report there: /tmp/obs-demo/gpu-box/work/dates-out/report.md

With a brief, the command returns after handing it to the native CLI. Claude Code accepts --agent and --permission-mode; Codex accepts --model, --effort and --sandbox. Defaults come from agents.claude and agents.codex in OAK’s preferences. A Codex start always adds its output folder to writable roots. OAK answers an initial folder-trust prompt by trusting the directory you named. Without --brief, agent start is the interactive launch path; a remote start then attaches the terminal there.

How agents share what they know

Agents can read the database before choosing where to work. oak query files groups edits by repository and path from its root, including other clones and worktrees. oak query search searches recorded asks and answers. oak query delegated reads the agents this machine tracks and their workers. oak query findings reads short facts posted by agents on any machine whose records have arrived.

oak query files --status pending
oak query search --text "generated parser"
oak query delegated
oak query findings --repo git:example.invalid/team/synthetic --path src/parser.ts

Every query includes freshness: whether local catch-up completed, when it last completed, and how far each machine’s records reach. An answer is evidence as of the last publication and sync. A recent local read does not make another machine’s evidence current. Reads are pull-only: querying never asks another agent to act and never sends a message. Use oak sync now when you need to pull newer records.

Post a finding

Use a finding for a short fact another agent should know. It carries its posting session, machine, time, repository and paths. Paths are relative to the repository root in the database, so a finding applies in other clones and worktrees too. Omit paths, or use --repo alone, for a fact about the whole repository. A path filter also includes repository-wide findings. Run inside a linked agent session, or name the posting session with --session.

oak finding add "src/parser.ts is generated from grammar.txt" --path src/parser.ts --session synthetic-session
oak finding add "Run the fixture generator before the tests" --repo --session synthetic-session
oak finding list --repo
oak finding list --path src/parser.ts --session synthetic-session --machine self
oak finding resolve <finding-id> --session synthetic-session

oak finding list and oak query findings show unresolved findings newest first; --all includes resolved ones. Reading accepts repository, path, session and machine filters. oak finding list --repo uses the current checkout; oak query findings --repo <key> takes its repository key. Posts and resolutions travel in the record log. Resolving a finding from another machine writes a retirement record here, which other machines see after pulling this machine’s records.

The agent list includes a findings count and quoted entries. The terminal Observatory and the editors’ Workers show a compact findings count with oak finding list beside it; the count covers unresolved findings held in the local database. “Unavailable” means the database could not answer. Findings are untrusted quoted data, never instructions. Check their source, scope and freshness before using them. Text output quotes and escapes the finding; JSON carries it as a string with trust: "untrusted".

Coordinate directly or sequence work

A parent can use oak agent tell <id> <text> to send a running agent a message. OAK records that message. Use it to coordinate a concrete overlap or pass a correction; a finding remains a fact to read, not a message delivery channel.

oak agent tell parser "Coordinate the parser changes with the docs agent before the next edit."
oak agent start --kind codex --brief /work/briefs/check-parser.md --after parser docs

oak agent start --after <id…> queues the new agent until the named agents are done. The agent has a queued state while it waits. Completion is evidence that work ended; it is not a review or approval of the result.

An edit-time heads-up

Before a Claude Code file edit or a Codex apply_patch, the capture hook can add one short context note when another active agent has unreviewed edits to the same repository path. It names the agent and machine, the pending edit count, when those edits began and the age of the evidence. It suggests coordinating through the parent or reading oak query. It never blocks the edit or changes a permission decision.

The database’s catch-up writes a small sidecar; the hook reads that file without loading SQLite or making a network request. Evidence older than 60 seconds, a missing or malformed sidecar, and local evidence that has changed since publication produce no note. An agent’s own edits, known descendants and finished agents are excluded. Codex records with unknown parentage are excluded too, so older records cannot produce a note about a possible descendant. A path and peer pair is mentioned at most once every three minutes. A shell command whose future file writes are unknown cannot get a path-specific advance note. Silence is not proof that a file is free: an unsynced change or a newly finished remote agent remains unknown until its records arrive.

How agent state is derived

OAK derives each delegated agent’s state itself from its report, linked session, raised hand, process and pane, transcript or rollout, and claude agents --json when available. These are separate from herdr’s pane statuses:

StateEvidence
startingThe native session has not linked yet.
workingA turn is in progress.
waitingThe turn ended without a completion report.
blockedA permission prompt, question or input wait needs a person.
erroredThe last turn stopped on an error; the row includes its message.
doneA nonempty report was written since the agent started.
goneThe process or pane ended without that report.

A report marks completion, not approval of the changes. Read and review it before merging. The terminal Observatory lists delegated agents and their workers; selecting an agent pins its conversation, and t opens its native tab on its machine. VS Code and JetBrains list delegated agents in Workers. Every session’s in-process workers have their own log and no herdr tab.

Select a worker in the Observatory or either editor’s Feed to follow its own log. From the shell, give the parent session and worker id; a remote log takes --machine too. Here the fixture records a reply and then the worker’s completion while the command follows it:

$ oak feed --kind agent --id check-login --session s-login --machine build-box --follow
Check the retry test  ● live · 03:35:39 · agent
Following worker log; no completion recorded yet.

03:35:39   said — The retry test passes with the synthetic fixture.
Worker ended at 2026-11-04T03:35:42.082Z (completed).

A completed worker’s log stays selected, with its recorded end time; a worker that resumes continues updating. Remote reads are at least ten seconds apart and failures are visible. Worker phases come from the call and its raised hand: a call with no result reads as awaiting permission while its permission hand is up, as awaiting input while the hand is an input wait, and as working otherwise.

Find who needs you

oak inbox and the terminal’s i overlay list raised hands, including those other machines’ records brought through sync. The editors show them in their session selectors and Sessions. Each names its machine and whether it needs permission, an answer or input. The terminal’s h jump selects the most urgent local hand; a remote hand still needs its native session. Open that agent’s tab with t from the Observatory and answer there. A synced hand describes the last published state, so its age matters.

Wait for completion or a blocked turn

oak agent wait <id…> defaults to --until done: every named agent must be done or gone, and any gone agent makes it exit 1. --until blocked returns when one is blocked or errored. --until any returns when one is neither starting nor working. A timeout exits 124. Local file watches wake the wait when evidence changes, with a two-second polling fallback; a remote agent is refreshed at most every three seconds.

The synthetic Codex turn first stops on an error:

$ oak agent wait dates --until blocked --timeout 20
dates  errored since 03:35:51  Cache parsed date formats
    codex · on gpu-box · read 03:35:51 over ssh · tab dates: Cache parsed date formats
    Synthetic provider is at capacity.

Handle an error or permission request in that agent’s native tab. This fixture then writes the three completion reports, after which the default wait succeeds:

$ oak agent wait docs login dates --timeout 20
dates  done since 03:35:51  Cache parsed date formats
    codex · on gpu-box · read 03:35:51 over ssh · tab dates: Cache parsed date formats
login  done since 03:35:51  Retry the login test
    claude · on build-box · read 03:35:51 over ssh · tab login: Retry the login test
docs  done since 03:35:51  Document the retry policy
    claude · this machine · tab docs: Document the retry policy

Review where the changes were made

Read each report and the checks it records. In the terminal app, select the agent’s session and open Review with F3. A remote session’s review reads and actions run on its machine. The shell uses the same review verbs, with --machine selecting the saved machine:

$ oak review --session s-login --machine build-box
s-login  whole session · 1 review unit(s)

#1 tests/login.test.ts +1/−1
Index: /tmp/obs-demo/build-box/work/app/tests/login.test.ts
===================================================================
--- /tmp/obs-demo/build-box/work/app/tests/login.test.ts
+++ /tmp/obs-demo/build-box/work/app/tests/login.test.ts
@@ -1,1 +1,1 @@
-test("login", run);
+test("login", () => retry(run, 3, 200));
$ oak keep 1 --session s-login --machine build-box
✓ kept edit #1 (tests/login.test.ts)

Keep records acceptance; it does not commit. Undo restores the captured previous content on that machine and refuses an unsafe overwrite when the file has changed since. Use oak diff, undo, redo, comment and quote with the same session and machine selection.

VS Code and JetBrains list each saved machine in Switch Session, the Timeline selector, Sessions and Workers. Their parallel background reads share one cache per machine, with the answer’s age, errors, a ten-second refresh interval and a 45-second deadline. Selecting a saved machine’s session reads its Review, Timeline and Overview there; keep, undo, redo, comments, quotes and prompts run there. Opening an edit shows its remote patch. Review supports prompt scopes, Search, Filter, Sort, and per-edit, per-file and whole-session decisions. File History follows the remote file selected in Review. Decorations and inlays use local editor files; Open all in editor is hidden for remote Review. A record from a machine that is not saved is read-only here, with an offer to fetch the session. See remote editor review for panel-specific limits.

Merge, then close the tabs

OAK does not merge. After review, commit the accepted changes in each agent’s checkout, fetch its branch into the integration checkout, and use your normal git merge or cherry-pick process. Run the combined checks there. oak sync shares session records and agent instructions; it does not transfer or merge repository changes. Keep, a completion report and a successful wait do not prove the branches integrate.

Once the work is integrated, close the native tabs. A closed row remains available with --all; closing an agent before its report marks it gone.

$ oak agent close docs login dates
Closed docs's tab; it stays listed under `oak agent list --all` (done).
Closed login's tab; it stays listed under `oak agent list --all` (done).
Closed dates's tab; it stays listed under `oak agent list --all` (done).
$ oak agent list
no delegated agents — `oak agent start --kind claude|codex --brief <file>` starts one

Use oak agent list --all to include the closed rows. Their reports, captured edits and review decisions remain available.

Share the record across the SSH mesh

Run oak sync now once on each machine to begin sharing the record. Thereafter capture hooks and pollers start background runs at most every five minutes while automatic sync is enabled. The first run may need another pass while a large local database builds.

$ oak sync now
oak sync: pulled 3 files, 8KB
  build-box   2 files, 6KB
  gpu-box     1 file, 2KB

Schema 5 added delegated, and the current database schema is 6. Its rows travel in the record log alongside sessions, prompts, answers, edits, workers, usage and raised hands. oak query delegated --all reads this machine’s tracked agents, including its remote pointers, and their workers; workers=false omits workers. To read agents independently started on every machine, join the table to machines. Filter d.machine IS NULL to select the owning machine’s records rather than also counting a caller’s remote pointer.

$ oak query sql "SELECT coalesce(m.saved_label, m.label) AS machine, d.id, d.state FROM delegated d JOIN machines m USING (machine_id) WHERE d.machine IS NULL ORDER BY machine, d.id" --json | jq -c ".rows[]"
{"machine":"build-box","id":"login","state":"done"}
{"machine":"gpu-box","id":"dates","state":"done"}
{"machine":"this machine","id":"docs","state":"done"}

A query’s own --machine filter takes the id, self, or the label you saved the machine under, and refuses any other name. coalesce(m.saved_label, m.label) gives the name in machine_label: the saved label where available, otherwise the machine’s own label. oak query files groups edits the same way, by repository and path from the repository’s root, across clones and worktrees. oak query search --text "retry" searches recorded asks and answers. Each answer includes freshness; it is evidence through the last publication and sync, not a live view of another process.

For delegated agents, a remote row can come from the database when sync has read that machine within ten minutes, otherwise from its own CLI over SSH; the row says how and when it was read. A saved machine’s general session listing has a stricter cache condition: sync read it within ten minutes, its records were read whole, nothing there was active in the last two hours as its records and the files the last run saw there say, and no hand raised there in the last day is still up. Otherwise OAK asks the machine over SSH.

Each machine publishes its own derived rows as its database catches up. Capture hooks request this at most once a minute and immediately when a raised hand changes. The Claude Code status line publishes through its oak usage call, on the renders that ask for the database’s totals (every render until those totals are whole, then about every ten minutes). A record segment is complete only at its writer’s sealed length or locally acknowledged append length. Bases retain purges, and writer lifetimes preserve ordering after a reinstall, including a clock rollback. oak doctor names a partly restored log and its recovery steps.

Usage and operating limits

Usage distinguishes a session’s own tokens from its total with agents. Dollars marked ~ are estimates at OAK’s versioned list prices; actual charges have no tilde. Schema 6 stores split cache-write counts and pricing context, and reprices old rows when the table changes. The month’s dollar figure follows its mo reset in status bars. Terminal and editor status bars omit the five-hour window; Stats, oak usage and the Claude Code status line retain it when the account has that limit. The status line compacts before wrapping in a narrow pane.

A remote herdr server must outlive the SSH login for work to continue after the laptop disconnects; Remote operation explains the host setup. A worker on the laptop stops while it sleeps. Neither OAK’s tracking nor sync keeps a sleeping machine’s processes running.

Sync carries recorded prompts, answers, paths, briefs’ control records and agent instructions to machines you trust. It does not carry login credentials. Any agent able to read the local database can read the shared record there. A synced state is the last recorded state; answering a permission request still requires the live native session. Database & sync covers retention, purges, backup encryption, conflicts and exclusions.
