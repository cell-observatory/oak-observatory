OAK builds a local database on each machine and exchanges session records with your other machines. If you run Claude Code or Codex across machines, this page explains how those databases, Secure Shell (SSH) connections and a shared backup folder fit together.

A session is an agent conversation. Its transcript records the conversation; the observatory’s store holds captured edits and file snapshots. Each machine derives a local database from those sources. The shared storage server holds an encrypted backup; each machine keeps and queries its own database.

Database & sync is the reference for commands, settings, file families and database tables. Multi-agent work across machines follows the workflow from starting agents to reviewing their changes. How agents share what they know covers findings, messages, dependencies and the edit-time heads-up.

The parts and their connections

Consider two synthetic machines, laptop and build-box. Each publishes the facts it derives into a record log, a sequence of changes that another machine can apply to its own database.

The database on each machine

The database holds session titles, workspaces, prompts and answers, edit metadata, tool-call metadata, workers, review comments and usage. It also holds plans, memories, skills and raised hands: recorded requests for permission, an answer or input. Rows retain the identity of the machine that published them.

The database contains searchable conversation text, but it does not contain tool output or the contents of captured file snapshots. Those remain in transcripts and the store. Reading a remote session’s title or searching its answers therefore does not require fetching its transcript.

Its location

The default database folder is ~/.claude/claude-observatory-index/. With CLAUDE_CONFIG_DIR set, that folder sits under the configured directory instead. The file is index-v1-<hash>.sqlite, where the hash identifies the store’s path. oak query --status reports its location.

The database sits beside the default store, outside the store itself. Moving the store changes the database’s filename without moving its folder onto the store’s destination. Keep the configuration directory on local storage; setting CLAUDE_CONFIG_DIR to a mounted share also puts the database there.

Its construction and recovery

A listing, search or query brings the database up to date with local sources and the record logs already on disk. The observatory tracks changed files and transcript read positions. A bounded catch-up can leave work for a background build; a query reports how current its answer is.

Deleting only the database leaves the transcripts, captured snapshots, record logs and backup key intact. The next catch-up rebuilds the database from the remaining sources and replays the logs, including this machine’s own log.

The archive consists of records in the database whose source files are gone. Its recovery depends on the record logs retaining those facts. If both the sources and all copies of their logs are lost, rebuilding cannot recover them. Deleting the database is therefore neither a backup procedure nor a way to forget a session everywhere. See the archive and deliberate deletion.

Queries across machines

oak query sessions lists sessions in the database; oak query search --text retry searches prompts and answers. oak query sql accepts a read-only SQL statement. These commands read the local database, including records previously received from other machines.

The following command ran against isolated synthetic homes for laptop and build-box. The build box’s record log was copied into the laptop’s store as a stand-in for transport; its transcript was absent there.

$ oak query sql "SELECT m.label AS machine, s.title FROM sessions s JOIN machines m USING (machine_id) WHERE s.archived_ms IS NULL ORDER BY m.label, s.title" --table
machine  build-box
title    Check the retry test

machine  this machine
title    Document the retry policy

2 rows · 196 ms · the database is current

A remote record describes the last published state. A raised hand in that record does not provide a live connection to its agent. Check the source freshness in the query response or oak query sync, and use the agent’s native session to answer it.

The exchange between machines

A saved machine is a machine registered with oak machine add. On a sync run, this machine asks each enabled, included saved machine for its inventory, a list of files it can supply. It then pulls the files its placement settings require over SSH. Save the machines on each other for exchange in both directions. Sync requires the same user name on both ends.

The record logs live at records/<machine-id>/ inside the store. Each machine appends changes to its own log; other machines copy those segments and replay them. A peer can supply logs it received from another machine. Compaction replaces complete segments with a base containing current records and deliberate deletions.

By default, record logs, edit logs, comments and agent records travel to every machine. Memories, plans, skills, agent definitions and commands also travel between machines. Full transcripts, Codex rollouts, snapshots and hook events stay on their origin and the configured backup until another machine fetches them. The reference describes placement overrides and exclusions.

When records travel

oak sync now runs one exchange. A peer asked for an inventory first catches up its database and publishes its own records within a bounded budget. A later run brings work that was not ready. Queries and listings also publish local changes; after sync has run, capture hooks can trigger background publication.

The first sync run with a usable configuration enables activity-triggered background runs, unless automatic sync is disabled. Hooks and pollers start throttled runs that pull and exit; failures delay subsequent background attempts. There is no continuously running sync daemon or additional listening port. SSH still requires access to each peer’s SSH service.

An offline machine

Previously received records remain queryable when their origin is offline. Another reachable peer can supply copies of its logs, but no peer can supply changes that never left the offline machine. A disconnected machine catches up on later runs.

oak sync fetch <session> retrieves a session’s content, trying its origin, the configured backup, then other available holders. A fetch requires a reachable copy. Later runs maintain fetched copies, subject to cache limits; a record in the database alone cannot reconstruct a missing snapshot.

A new machine

Install the observatory and save the peers it should read. Run oak sync now to receive their record logs, then query the new machine’s local database. Full session content remains subject to placement and explicit fetching.

To use the shared backup, mount its folder and obtain its existing key from a trusted machine. Each machine configures the folder’s path as mounted there. Merely mounting the folder does not populate a new machine with all other machines’ files: ordinary backup reads restore its own files and update copies already present.

A reinstalled machine

The observatory identifies a machine from its host name and home path. A reinstall using both again finds the old backup record, but it must explicitly take ownership before restoring or writing it. Recover the key first, then use oak sync setup --folder /mnt/team-share/oak-backup --restore and oak sync now.

The restore brings back eligible files belonging to that machine, including its record logs; its local database then rebuilds. Retention, exclusions and previous cleanup affect what returns. A different host name or home path creates a different identity, so --restore is not a selector for an arbitrary old machine. See backup setup and recovery.

The shared storage server

A backup target can be a saved machine or a folder. A saved backup machine pulls content over SSH. A backup folder can be a mounted network share such as /mnt/team-share/oak-backup; each client reads and writes that folder through the filesystem. The folder needs no observatory process or database service on its server.

Files and encryption

With the default placements, the folder receives transcripts and their session files, rollouts, captured snapshots and events, edit logs, comments, record logs and shared instruction files. The client splits content into objects and writes encrypted manifests describing how to reconstruct each file. Families set to off and files refused by sync’s credential guards are omitted.

The client encrypts objects and manifests with AES-256-GCM, the Advanced Encryption Standard in Galois/Counter Mode. Keyed hashes name machines and objects; original file paths are inside encrypted manifests. The folder also contains a format marker with an encrypted key check. Its structure and file sizes remain visible to the storage server.

The client verifies authentication and content hashes when reading. A wrong key or altered content produces an error. Removed content can remain encrypted in stored objects: the backup folder does not reclaim those objects when a session is deleted. See what the backup folder holds.

The backup key

The key lives at sync/key inside each participating machine’s store. The observatory creates it for a new backup folder and restricts its file permissions to the owner. It refuses a backup folder that would contain the key.

Another machine obtains that same key with oak sync key --from laptop, using its saved label for the machine that has it. This transfer uses SSH. Alternatively, oak sync key --import reads a saved key from standard input. Keep a separate copy through oak sync key --show; losing every copy makes the encrypted backup unreadable.

The key stays outside the backup folder, but it follows the store if you move the store. Keep the store on storage you control, apart from the shared backup. Backup encryption protects stored copies; machines with the key can decrypt the shared record.

Reads and exclusions

During a sync run, the client reads encrypted manifests and the objects needed to restore its own files or update copies it already holds. An explicit fetch can retrieve another machine’s session from the folder while its origin is offline. Decryption and database updates happen on the client.

Sync excludes the SQLite database, backup keys and credential files, including agent login credentials and SSH keys. It does not back up your entire working tree or configuration directory. Session text and instruction files can themselves contain sensitive information; encryption does not remove that text.

Why the database stays local

  • Database coordination stays on one machine. The database opens SQLite in write-ahead logging mode, with journal and shared-memory files beside it. Its location deliberately stays outside a store that can move to a network share.
  • Each machine tracks its own sources. The database records local paths, file identities and read positions. Record logs exchange the derived facts that another machine can apply to its own database.
  • Received records remain available offline. A query can read the local database without reaching the origin or mounting the backup. Its answer remains limited to records already received.
  • Recovery uses files and logs. Sync explicitly excludes the database directory. The backup supplies encrypted source files and record logs, from which the client rebuilds a database instead of opening a shared database.

For setup, keep each configuration directory local, save trusted peers, and configure the same backup folder and key on participating machines. Use Database & sync for the exact commands and settings.
