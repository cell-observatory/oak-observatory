The Timeline panel presents the session as it unfolded — four tabs, one selector. Where the Overview organizes by worktree and change, the Timeline organizes by the conversation and the agent's own actions.

Feed

The Feed tab is the selected conversation as it happened: your prompts on grey bands, the agent's replies as prose, its thinking folded until you open it, every tool call with the diff it produced, and the permissions it asked for — read from the native transcript and followed as it grows. Picking a worker, a workflow run, a task or a background shell in the Overview points the same tab at that thing's own activity; when the source finishes, the same view becomes its audit log. Scrolling back holds that position and offers a ↓ newest control — shown only while the view is away from the tail — to return to it. New Session starts an agent through herdr. Review comments and quotes prepare a draft; an explicit Send submits it to a matching live pane.

Prompts

Prompts is one row per thing you asked, in order, each printed whole with its edits, files, tokens, and duration. Selecting a prompt scopes the Overview beside it — the fleet, the tasks, and the whole change map narrow to the work that prompt caused.

Observations

Observations pairs each edit with the reasoning the agent recorded near it, flags notable content (debug statements, possible secrets, large deletions), and names what shaped the session in its Context section — each entry labeled by whether the transcript proves it or the file is merely present.

Actions

Actions is the typed timeline of every tool call, grouped by kind, with low-signal categories collapsed and errors surfaced. It opens with any live conflicts and closes with the two audits — risk and egress.

Choosing a session

The Timeline selector and Switch Session use one order across machines. Newest is the default; raised hands (“needs you”) and sync conflicts lead wherever they are shown. Search matches session titles, ids, workspaces, models and machine names. In the Timeline’s VS Code selector and both editors’ Overview Sessions tabs, Active and all four Sort choices apply across machines. Sessions known only from the local sync database join the same list with their machine badge.

A session on another machine

In VS Code and JetBrains, the session selector and Switch Session merge this machine’s sessions with every saved machine’s sessions in one list, newest by last activity first. Each remote row keeps its machine badge; each machine’s read, sync, refresh or failure state stays on one line above the rows (the Overview describes how they are read). Picking one reviews that session on its machine, as the terminal app does: session reads and review verbs run with --machine. The selector names the machine beside the session. Stats reads that session’s own and with-agents tokens on the selected machine and labels them with its name; account history and account usage remain read on this machine, in separately labelled sections. Feed, Prompts, Observations and Actions are read there, and Observations and Actions say when. Opening an edit or file first uses a verified mount in this window, then the editor’s SSH remote window. Keep, Undo, Redo and Resolve run on the session’s machine. Review retains its list, filters, counts and prompt scopes; File History follows the selected remote file or mapped editor file. Diff stays available in this window. See Review a session on another machine.

💡
Grouped, when you want it

The Timeline can show all four of Feed, Prompts, Observations and Actions side by side, and carries its own session selector above the tabs so moving between two live conversations is one click.

Remote tasks, search, navigation and replies

Task Keep, Undo, Clear and Clear Completed run on the selected machine through task-keep, task-undo and task-clear --machine. A failed remote action reports its reason and never falls back to a local task.

Search Conversations searches this machine and enabled saved machines concurrently, with the shared 45-second remote deadline and five seconds for the CLI to return. Each hit names its machine; opening it reviews the session there. Results from machines that answered remain available when another fails, with that failure named.

Keyboard review walks remote display units using the same mount-first, then SSH route. Press Ctrl+Alt+X (Cmd+Alt+X on macOS), then N/P for next/previous edit or Right/Left for next/previous file. With Reveal Next on Resolve enabled, a single Keep or Undo continues after a fresh read confirms the change was resolved.

Reply from Timeline/Feed, quotes or review comments. Review has no reply box.

Review a session on another machine

Select a session from a saved machine (oak machine list --json). Open all in editor opens a stacked review in this window, ten changes per page. Each page is read in one bounded call to the saved machine; Keep, Undo and Redo run there and refresh the block. A file that no longer exists still shows its recorded change. The side-by-side switch uses a verified mount when available and the recorded before/after otherwise. Open on <machine> and the filename first use a matching mounted share for editing. OAK matches Linux or macOS mount tables against the saved host, its home share, or a network share mounted on both machines. A local file with the same pathname is not enough. The mounted files are editable, with highlights, inline review controls and File History. Keep, Undo, Redo and Resolve still run with --machine; OAK refreshes after each action because SMB notifications can lag.

Without a matching mount, VS Code and Cursor open a new Remote-SSH window at the session’s workspace, using the saved machine’s SSH target. JetBrains uses Gateway / Remote Development over SSH. OAK writes a request on that machine, valid for ten minutes and consumed once by the remote editor, to select the session and open the edit or file. The remote window uses its real files and normal OAK highlights, inlays and Open all view.

If OAK is missing on the remote editor server, the editor offers to run oak install-extensions --machine <label> there. Connect once first if the editor has not installed its server. JetBrains needs an installed remote IDE to build its documented Gateway connect link; if it cannot build the link, or Gateway does not open, the dialog gives the SSH target, workspace and steps for File → Remote Development → SSH → New Connection. After an expired request, select the session in that window’s OAK.

This window still lists remote edits, prompt scopes, counts and history, and runs review actions on their machine. Diff is a separate action: it opens the editor’s before/after viewer using contents read from that machine, with a patch fallback for older CLI versions. Replies remain in Timeline/Feed, quotes and review comments; Review has no reply box.

Open workspace window

In Observatory’s Sessions list or a session picker, choose Open workspace window (the window button in VS Code/Cursor; right-click the row in JetBrains). The session’s folder opens in its own editor window. Saved machines use Remote-SSH in VS Code/Cursor or Gateway in JetBrains, with SSH instructions if Gateway cannot open. A missing folder or a session with no workspace is refused. One action opens one workspace.

The window pins the session and opens its pending changes in the stacked editor, ten per page. With nothing pending, OAK says so and opens no empty tab. It reveals Review, File History and the Observatory Timeline, and focuses the Overview with Sessions, Workers, Processes, Tasks and Workflows side by side and the change map beside them. Your saved view placements stay in place. A terminal named OAK runs oak; an existing OAK terminal is reused. JetBrains needs its Terminal plugin for that terminal. An already-open workspace receives the same request without restarting the editor; a request is used once and expires after ten minutes.

Use one window per machine and workspace instead of combining mounted folders in a multi-root workspace. OAK, git and file watching then run on the machine that owns the files, and a stalled extension host affects only that window.
