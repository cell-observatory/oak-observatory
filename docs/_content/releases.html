OAK ships on two channels — a stable channel of tagged releases and a rolling pre-release channel off the dev branch. Both update the same way, from one chip in the editors or one flag in the terminal. Every release's changes are in the changelog.

The two channels

Stable

Tagged releases, cut from main — each one a version like v0.10.0. The full three-OS test matrix and the end-to-end suite ran on the exact commit; the artifacts (CLI tarball, VS Code .vsix, JetBrains plugin zip) are attached to the GitHub Release; and the changelog names what changed. This is the default channel — releases/latest serves it, and nothing on it ever moves after it's published.

Pre-release

A rolling build of the dev branch. Every push to dev rebuilds all artifacts, stamps them <next>-dev.<n> (for example 0.11.0-dev.37), and refreshes one GitHub release — tag dev-latest, marked prerelease, so the stable channel never sees it. You get merged features and fixes days or weeks before a tagged release, with correspondingly less soak time.

ℹ
Real semver ordering

Every dev build is newer than the stable it forked from, and the eventual tagged release is newer than every dev build that led to it — so promotion lands as an ordinary update, never a downgrade.

Switching & updating

Both editors pin a version chip at the right edge of the Overview's toolbar. It shows the version you're running, and a dot appears when what is installed differs from the newest release of the channel you follow, in either direction: a newer release, or an install that sits above the channel (one left on pre-release after switching to stable). Each editor compares its own build and the CLI, which oak version --check reports on. Its menu lists what each surface currently has — the CLI, both editor plugins, and the status line carry independent versions — and offers Update now, which installs the newest release of your channel in one pass, then offers the reload or restart that loads it. A CLI linked to a source checkout, or copied to a machine by oak machine add, is offered no release, and its row in the menu says which. Nor is a local build offered one: a CLI, extension or plugin whose version ends in -dev.0, which every build of a dev checkout carries and no release does. Its row says local build, no dot appears for it, and Update now leaves it alone, as oak update does. The JetBrains IDE's own plugin updates read the plugin repository rather than OAK, so an IDE subscribed to it can still offer the repository's build over a local build of the plugin; decline it there to keep the local build.

From the terminal, the same in two commands:

oak version --check   # does my install match my channel's newest?
oak update            # install it — everything OAK installed, here and on saved machines

oak update covers the CLI; the extension in every VS Code-family editor and Remote-SSH server that has it; the plugin in every JetBrains IDE that has it; the Claude Code capture hooks in your user settings and the Codex capture hooks, where a hook you turned off in Codex stays off; the bundled status line; herdr, its integrations and OAK’s herdr plugin, where herdr publishes a build; and a focus server still running an older build. A CLI linked to a source checkout (npm link, npm i -g ./packages/cli or ./install.sh) is left alone, since installing a release over the link would replace it with a copy: its row names the checkout, where git pull and npm run build update it. A project’s own .claude/settings.json is shared through its repository, so oak update never writes to it: one that needs a repair gets a row naming the oak init --repair to run there. It then runs oak update --here on each enabled saved machine over ssh, in parallel and once for machines saved with the same ssh target, where OAK downloads the release itself. On a machine oak machine add provisioned, the CLI is the copy it pushed, which oak update leaves alone: that machine’s row names the oak machine add that updates it. A local build (-dev.0), here or on a saved machine, is left alone too, unless you pass --force or --channel, which replace it with that channel's newest. It prints one plan and one result table, leaves what is already current alone, and exits non-zero when anything could not be updated, on any machine. --here updates this machine only, --check previews, and --json returns the plan as data. The editors’ Update now runs the same command, so it updates the saved machines too.

💡
Following a channel means matching it

A surface is refreshed whenever its version differs from the channel's newest, in either direction — so switching from pre-release back to stable steps you down to stable cleanly, not only forward.
